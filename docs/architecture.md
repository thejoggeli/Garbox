# Architecture and code generation

## Layering

```text
YAML application/hardware config + XML GUI descriptions + PNG resources
                              │
                              ▼
                    Python/Jinja generator
                              │
          ┌───────────────────┼────────────────────┐
          ▼                   ▼                    ▼
 generated framework     generated GUI       generated hardware
 bindings and routing    object trees/assets  singleton instances
          │                   │                    │
          └──────────────┬────┴────────────────────┘
                         ▼
             handwritten application layer
     behaviours · controllers · screens · providers
                         │
                         ▼
              reusable modules (“parts”)
                         │
                         ▼
     core runtime · utilities · LVGL · ESP32 hardware
                         │
                         ▼
          SHT31 · fan · heater · encoder · display
```

Dependencies generally point downward. The generated runtime is the composition root that knows every concrete application component.

## Configuration as the topology source of truth

`codegen/config/application.yaml` defines the global runtime:

- app name;
- initial behaviour and screen;
- event-pool and queue capacities;
- tick period and ordered phases;
- maximum event/state dispatch depth.

`events.yaml` and `states.yaml` define typed messages and shared stores. Core runtime events/states are merged from `config/core`.

`controllers.yaml`, `behaviours.yaml`, and `screens.yaml` declare each component’s:

- directory;
- tick phases;
- sent and received events;
- read and written states;
- renderer and render functions for screens.

`hardware.yaml` declares named peripheral instances and their parameters. `devtools.yaml` adds profiler IDs. XML files in `config/gui` describe LVGL object trees, reusable XML components, styling, images, and initialization calls.

The loader normalizes these sources into an object graph. It resolves which components read/write each state, which components send/receive each event, which components run in each phase, and which C++ files/types are required.

## Generator pipeline

The generator entry point is `codegen/src/main.py`.

1. Find and merge all YAML files.
2. Load all GUI XML documents.
3. Normalize hardware names and references.
4. Parse events and payload fields.
5. Parse states and fields.
6. Preprocess XML shorthand, expand reusable XML components, resolve images, and turn attributes into wrapper method calls.
7. Resolve application/component relationships and validate many references.
8. Save normalized diagnostic JSON/XML under ignored `codegen/output`.
9. Delete and recreate `src/generated`.
10. Generate hardware, shared types, states, component bases/bindings, runtime, global config, GUIs, and binary image sources.
11. Refresh marked generated sections in handwritten component headers.
12. Create missing `.cpp` component stubs without overwriting existing implementations.

The review’s clean-room run generated byte-identical copies of:

- `src/generated`;
- `src/shared`;
- `src/bin`;
- every generated section in handwritten app headers.

That means the current checked-in generated sources and the current config/templates agree.

## Generated versus handwritten contract

Generated files provide the repetitive, topology-dependent code:

- enum IDs and string conversion;
- event payload structures and aliases;
- state storage/getters/setters/publication;
- per-component state bundles;
- abstract component interfaces with only declared handlers;
- typed event construction and sending helpers;
- direct event/state routing;
- component/state construction and binding;
- phase handler functions;
- hardware singleton construction;
- GUI object construction and styling.

Handwritten files provide policy and behavior:

- each controller’s hardware interaction;
- high-level behavior logic;
- screen interactions and dynamic rendering;
- physical part implementations;
- safety decisions and calibration;
- application task/startup policy.

Generated sections in component headers are delimited by `GENERATED BEGIN/END`. The generator replaces only those sections. Existing `.cpp` implementations are never overwritten.

## Runtime lifecycle

```text
setup
  ├─ hardware init
  ├─ physical parts init
  ├─ display/LVGL init
  ├─ auxiliary tasks start
  ├─ startup animation
  ├─ Runtime construction
  │    └─ construct states + all components
  ├─ Runtime::init
  │    ├─ inject host into states/components
  │    ├─ component onInit hooks
  │    └─ activate initial behaviour and screen
  ├─ main task start
  └─ Runtime::start
       ├─ every component onStart hook
       └─ generated tick runner loop
```

All controllers, behaviours, and screens are initialized and started. Enabled/active status controls routing and visibility, not object lifetime.

## One application tick

```text
tick start: Time snapshot, profiler, queued behaviour switch
  │
  ├─ Heartbeat handlers ──► dispatch states/events until stable
  ├─ SensorRead handlers ─► dispatch states/events until stable
  ├─ UserInput handler ───► dispatch states/events until stable
  ├─ active Logic handler ► dispatch states/events until stable
  ├─ ActorWrite handlers ─► dispatch states/events until stable
  ├─ Logging handlers ────► dispatch states/events until stable
  ├─ wait to +20 ms
  ├─ Render controller ───► dispatch states/events until stable
  │
tick end: counters and profiler
wait until 33 ms period boundary
```

The phase order is meaningful. For example, a fresh sensor state can be published during `SensorRead`, consumed by the fermentation behaviour in `Logic`, converted into commands, and applied by actuator controllers before or during `ActorWrite`, all inside one tick.

## State flow

A generated state contains three records:

- `mNext`: values being written;
- `mCurrent`: last published values read by normal getters;
- `mLast`: values from before the most recent publication.

The intended flow is:

```text
writer setter → update mNext → mark state dirty once
             → runtime publish → mLast = mCurrent; mCurrent = mNext
             → generated reader callbacks
```

Generated bindings enforce a single declared writer per state and expose const state references to readers. `StateLogScreen` observes all state publications independently of the active screen.

## Event flow

```text
component makeXEvent()
  └─ EventFactory allocates EventBlock<X> in fixed pool
       ├─ generated payload (value initialized)
       └─ header: ID, type, sender, routing flags

component sendEvent(event)
  └─ Runtime queues pointer
       └─ generated switch routes a typed EventView<X>
            ├─ always-on controller receivers
            ├─ active behaviour receiver(s)
            ├─ active screen receiver(s)
            └─ EventLogScreen observer
```

The design avoids per-event heap allocation, string lookup, listener maps, and unsafe payload casts in application code. Configuration determines the routing switch at generation time.

## Concurrency model

The high-level application runtime is single-threaded in `MainTask`, but display transport and feedback are concurrent:

| Task | Purpose | Core / priority |
|---|---|---|
| Main | 33 ms component tick and routing | Core 1 / 5 |
| PiezoPlayer | tone/sequence progression | Core 1 / 18 |
| LED animation | status LED animation | Core 1 / 17 |
| Display render | LVGL timer/render work | Core 1 / 1 |
| SPI DMA | SPI transaction processing | display core / 2 |
| Display sender | display flush sequencing | display core / 3 |

The display uses three internal DMA-capable partial buffers, a three-entry FreeRTOS queue, a counting semaphore for buffer ownership, and a DMA barrier between the sender and asynchronous SPI completion.

This separation keeps slow display transmission outside the deterministic application loop, but makes shutdown and ownership correctness important.

The display side is itself a substantial vertical architecture: an XML UI compiler emits typed object trees and image arrays; generated screen bases schedule semantic dirty updates; custom widgets/helpers sit on a C++ LVGL façade; and the runtime connects LVGL partial rendering to an ST7789 and chunked SPI-DMA transport. Its construction, concurrency contract, and detailed review are documented in [The custom LVGL stack](lvgl-stack.md).

## Architectural judgment

The architecture is internally coherent and more intentional than its repository documentation suggested. Its best idea is using code generation to turn a declarative topology into narrow, typed component interfaces and direct routing. This makes dependencies visible and prevents much accidental coupling.

The cost is that a small appliance now owns a framework, a generator, a UI DSL, hardware wrappers, containers, and several schedulers. That cost is acceptable only if the framework stops expanding and receives tests. For finishing Garbox, the framework should be treated as infrastructure to stabilize, not a product to keep generalizing.
